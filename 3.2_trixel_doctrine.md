## 1. Executive Summary

Trixel establishes a fundamentally different approach to generating three‑dimensional geometry from two‑dimensional artwork. Unlike conventional mesh‑deformation systems that begin with geometry and apply continuous transformations, Trixel begins with discrete addressable cells and compiles them into geometry through explicit topology decisions.

The system operates on a foundational premise: **the discrete visual cell owns geometry, not the reverse.**

This document formally defines the architectural principles, invariants, acceptance criteria, and implementation requirements for the Trixel compiler.

---

## 2. Core Philosophy

### 2.1 Architectural Distinction

| Conventional 3D Systems | Trixel Compiler |
|-------------------------|-----------------|
| Existing geometry → deformation | Source pixels → topology decisions |
| "Where should these vertices move?" | "What geometry does this pixel own?" |
| Visually acceptable approximation | Attributable, traceable construction |
| Continuous deformation | Discrete topology policy |

### 2.2 The Foundational Statement

```
Trixel does not deform artwork into geometry.
Trixel compiles discrete visual cells into geometry while preserving
their identity, declared metric, and provenance through every topology
decision.

When exact one‑to‑one preservation is impossible, the compiler must
apply an explicit, deterministic, inspectable topology policy.
```

## 3. Key Definitions

### 3.1 Cell Disposition

Every source pixel receives a **topology disposition** that describes how its identity and coverage are handled in the compiled geometry. Additional facets (visibility and structural roles) are recorded separately.

#### Topology Disposition

| Disposition | Definition |
|-------------|------------|
| **PRESERVED** | The source cell retains one distinct canonical ownership region with its declared intrinsic metric. |
| **MERGED** | Multiple cells are combined into one ownership region. |
| **SPLIT** | A single cell is expanded into multiple ownership regions. |
| **CULLED** | The cell is removed by explicit policy. |

#### Visibility State (orthogonal)

| State | Definition |
|-------|------------|
| **VISIBLE** | The cell contributes to visible surfaces. |
| **OCCLUDED** | The cell is hidden but preserved (e.g., internal faces). |

#### Structural Roles (optional, multiple)

| Role | Definition |
|------|------------|
| **CAP_CONTRIBUTOR** | Cell participates in boundary closure (e.g., end caps). |
| **TRANSITION_CONTRIBUTOR** | Cell participates in a topology change (e.g., taper step). |

**Record format:**
```json
{
  "topology_disposition": "PRESERVED",
  "visibility_state": "OCCLUDED",
  "structural_roles": ["CAP_CONTRIBUTOR"]
}
```

### 3.2 Ownership Hierarchy

| Element | Owner |
|---------|-------|
| Preserved geometry | One source cell |
| Merged geometry | Declared source cells (joint) |
| Split geometry | One source cell (multiple elements) |
| Transition/Cap geometry | Compiler policy + boundary provenance |

**Critical Rule:** Geometry cannot acquire visual authority merely by existing. Every canonical geometric element must derive its authority from either:
1. One or more addressed source cells, or
2. An explicitly declared structural topology rule.

### 3.3 Adjacency Distinction

Three distinct concepts must be separated:

| Concept | Definition |
|---------|------------|
| **Source adjacency** | Neighbor relationship in original discrete footprint |
| **Compiled adjacency** | Neighbor relationship after explicit topology decision |
| **Geometric proximity** | Elements spatially near one another |

**Authority Direction:**
```
cell adjacency → authorizes → topological incidence → embodied as → shared geometric edge
```

**Prohibited:** `shared geometric edge → inferred afterward → cell adjacency`

## 4. Architectural Layers

The Trixel architecture comprises five distinct layers:

```
┌─────────────────────────────────────────────────────────────┐
│                    1. Address/Lattice                       │
│  Defines exact cell identity, footprint dimensions,         │
│  intrinsic metric, addressing, and neighbor vocabulary.     │
├─────────────────────────────────────────────────────────────┤
│                    2. Artwork Authority                     │
│  Assigns color, palette role, material intent, and          │
│  metadata to addressed cells.                               │
├─────────────────────────────────────────────────────────────┤
│                    3. Topology Authority                    │
│  Preserves or explicitly transforms identity, adjacency,    │
│  occupancy, seams, and cell disposition.                    │
├─────────────────────────────────────────────────────────────┤
│                   4. Geometry Authority                     │
│  Embodies authorized cell graph as canonical positions,     │
│  edges, faces, normals, and UV mappings.                    │
├─────────────────────────────────────────────────────────────┤
│                   5. Render Expansion                       │
│  Duplicates or reorganizes canonical geometry for           │
│  engines, format, and rendering requirements.              │
└─────────────────────────────────────────────────────────────┘
```

## 5. The Cell Footprint

### 5.1 Definition

A **CellFootprint** is the fundamental primitive of Trixel. It contains:

```
dimensions
local cell addresses
adjacency stencil
orientation convention
cell metric
optional artwork payload
```

### 5.2 Immutability Invariant

```
CELL FOOTPRINT IS IMMUTABLE
```

The footprint is immutable in intrinsic space. Its embedding may change in extrinsic space.

A footprint may be:
- **Translated**
- **Rotated**
- **Mapped** onto a curved manifold

But it may **not** be continuously deformed without invoking a topology policy.

### 5.3 Embedding vs. Topology Operation

| Operation Type | Effect |
|----------------|--------|
| **Embedding** | Preserves footprint's intrinsic cell structure |
| **Topology Operation** | Changes footprint's intrinsic cell structure |

**Example:** A rectangular footprint can be embedded isometrically on a perfect cylinder when its declared width matches the cylinder circumference and the embedding preserves its intrinsic metric. A taper, sphere, or irregular tree trunk requires explicit topology decisions.

### 5.4 Footprint Instance

```
FootprintDefinition
    immutable local lattice and payload

FootprintInstance
    identity, placement, orientation, and target surface

TopologyDecision
    any authorized departure from direct embedding

GeometryRealization
    canonical positions and primitives produced from those decisions
```

#### Instance Specification Example
```json
{
  "footprint_definition": "bark_tile.16x16.v1",
  "footprint_instance": "trunk.segment.004",
  "local_dimensions": [16, 16],
  "cell_metric": [1.0, 1.0],
  "adjacency": "grid.cardinal_and_diagonal.v1",
  "embedding": "cylinder_wrap.v1",
  "topology_policy": "preserve_exact.v1"
}
```

#### Tapered Instance Example
```json
{
  "footprint_instance": "trunk.segment.005",
  "embedding": "tapered_trunk.v1",
  "topology_policy": "discrete_circumference_reduction.v1"
}
```

## 6. Compiler Invariants

### 6.1 Core Invariants

```
EVERY_CELL_HAS_EXACT_ADDRESS
EVERY_ADDRESS_IS_UNIQUE_WITHIN_ITS_INSTANCE
FOOTPRINT_DIMENSIONS_MATCH_DECLARATION
FOOTPRINT_INTRINSIC_METRIC_IS_IMMUTABLE
SOURCE_ADJACENCY_IS_DETERMINISTIC
```

### 6.2 Disposition Invariants

```
EVERY_CELL_HAS_TOPOLOGY_DISPOSITION
EVERY_CELL_HAS_VISIBILITY_STATE (if applicable)
EVERY_ADJACENCY_CHANGE_IS_POLICY_AUTHORIZED
NO_PROXIMITY_DERIVED_ADJACENCY
NO_UNDECLARED_SEAM
NO_UNDECLARED_MERGE
NO_UNDECLARED_SPLIT
NO_UNDECLARED_CULL
```

### 6.3 Geometry Invariants

```
EVERY_CANONICAL_PRIMITIVE_HAS_OWNERSHIP_OR_STRUCTURAL_PROVENANCE
COMPILED_CELL_GRAPH_MATCHES_DECLARED_TOPOLOGY
CANONICAL_GEOMETRY_EMBODIES_COMPILED_CELL_GRAPH
RENDER_EXPANSION_PRESERVES_CANONICAL_OWNERSHIP
COMPILATION_IS_DETERMINISTIC
```

### 6.4 Metric Invariant

```
A preserved pixel owns a world‑space footprint of the declared size.
```

### 6.5 Provenance Invariant

```
Every canonical primitive identifies either:
1. the addressed source cell or cells that own it; or
2. the declared structural topology rule that created it,
   together with its boundary‑cell provenance.
```

### 6.6 Completeness Invariant

```
Every source pixel receives exactly one topology disposition, one visibility state, and zero or more structural roles.
```

## 7. Seam Management

### 7.1 Seam Declaration

Wrapping a footprint around a closed surface requires explicit seam declaration:

```
east neighbor of column 15 = column 0
west neighbor of column 0 = column 15
```

### 7.2 Cell vs. Corner Addresses

| Address Type | Ownership |
|--------------|-----------|
| **Visual‑cell address** | Owns artwork and cell identity |
| **Corner‑sample address** | Owns canonical geometric sample positions |

**Note:** A corner sample is not promoted to visual owner simply because several cells reference it. A regular 16×16 cell footprint uses 17×17 corner samples in the standard quad realization.

## 9. Acceptance Gates

### 9.1 Mandatory Validation Checks

| Gate | Description |
|------|-------------|
| **EVERY_SOURCE_PIXEL_HAS_DISPOSITION** | All pixels explicitly handled |
| **EVERY_CANONICAL_PRIMITIVE_HAS_PROVENANCE** | All geometry traceable |
| **NO_UNDECLARED_PIXEL_LOSS** | No accidental cell deletion |
| **NO_UNDECLARED_PIXEL_MERGE** | No implicit merging |
| **NO_UNDECLARED_PIXEL_SPLIT** | No implicit splitting |
| **PRESERVED_PIXEL_METRIC_WITHIN_CONTRACT** | Metrics maintained |
| **TOPOLOGY_POLICY_IS_DECLARED** | Policy explicitly chosen |
| **COMPILATION_IS_DETERMINISTIC** | Repeatable results |
| **RENDER_EXPANSION_DOES_NOT_CHANGE_CANONICAL_OWNERSHIP** | Rendering preserves identity |

### 9.2 Verification Mechanism

The compiler must implement a lattice‑connectivity traversal:

```
START at addressed cell
TRAVERSE authorized cardinal adjacency
COLLECT reachable cells
COMPARE with declared ownership region
```

This detects:
- Holes introduced accidentally
- Disconnected cells
- Unwanted seam breaks
- Unintended cross‑fold adjacency
- Missing transition cells
- Duplicated occupancy
- Topology decisions inconsistent with resulting connectivity

**Verification Assertion:**
```
DECLARED_CELL_GRAPH_EQUALS_COMPILED_CELL_GRAPH
GEOMETRY_EMBODIES_COMPILED_CELL_GRAPH
```

## 10. Blender's Role

### 10.1 Redefined Authority

| Blender Role | Authority Level |
|--------------|-----------------|
| Blender experiment | Visual and geometric evidence |
| Blender modifier | Comparison implementation |
| Blender output | Candidate reference artifact |
| **Trixel contract** | **Authority** |
| **Trixel compiler** | **Construction authority** |

### 10.2 Critical Insight

Continuous deformation eventually violates discrete pixel ownership. This is not a failed experiment—it locates the boundary where a deformation system stops being sufficient and a topology compiler becomes necessary.

## 11. Prohibited Operations

The following operations are strictly prohibited:

```
Geometry MUST NOT invent cell identity.
Geometric proximity MUST NOT create adjacency.
A mesh weld MUST NOT merge ownership.
A mesh split MUST NOT split ownership.
A UV seam MUST NOT break logical adjacency.
A material boundary MUST NOT redefine topology.
A renderer MAY duplicate or reorganize render vertices,
but MUST NOT create, destroy, merge, or split visual ownership.
A footprint embedding MUST preserve intrinsic cell structure.
Any operation that cannot preserve intrinsic cell structure MUST invoke
an explicit topology policy.
Every topology change MUST preserve provenance and record its effect on
adjacency.
```

## 12. The Flood Fill Proof

The Aseprite brush analogy provides a powerful validation mechanism:

```
Every painted pixel has a deterministic address in a discrete lattice.
```

**Trixel Equivalent:**
```
Every visual cell has a deterministic address in a discrete geometric lattice.
```

Flood fill succeeds because:
- Every occupied cell has an exact address
- Neighbor traversal is deterministic
- Boundaries are made from discrete occupancy decisions
- No half‑cells or "almost‑neighbors" exist
- Connectivity does not depend on visual approximation

## 13. Core Doctrine

```
Trixel begins with an addressable discrete footprint, not a mesh.

Artwork assigns visual meaning to its cells.

Topology determines how cell identity and adjacency survive construction.

Geometry embodies those authorized decisions in space.

Rendering may reproduce the embodiment, but it may not redefine the
footprint, its ownership, or its topology.
```

**Fundamental Law:**
```
The discrete world exists first.
Geometry is its embodiment—not its authority.
```
